# History Suite: Self-Generated Anchoring

## What the previous History suite did

The previous History suite (**Paradigm P2** in the benchmark) simulated anchoring via conversation history by **injecting** a prior assistant estimate into the prompt:

- **Control**: No history; only the task with full evidence.
- **Low/High**: A prefabricated "Chat history" block was added where the *assistant* stated: "I would initially estimate around {anchor_value}."

The anchor value was **experimenter-chosen** (e.g. `theta ± 30`), not produced by the model. So it was an **approximation** of self-generated anchoring: it measured sensitivity to a number in history, not anchoring to the model's *own* prior estimate.

## Why it was only an approximation

- The prior in history was **fixed by the benchmark**, not generated by the model.
- The setup was equivalent to external anchoring (a number in the prompt) presented as a fake dialogue.
- True self-generated anchoring (Epley & Gilovich) requires the anchor to come from the **subject's own** initial estimate, with revision after more evidence.

## What the two-stage design does

The History suite implements a **two-stage protocol**:

1. **Stage 1**: The model sees partial evidence (or a warmup case) and gives an estimate.
2. **Stage 2**: The model sees full evidence (or the target case) with Stage 1 in the conversation history and gives a second estimate.

The **anchor is the model's Stage 1 answer**. Anchoring is measured as insufficient revision toward the evidence-supported answer in Stage 2.

- **Same domains**: History uses the **same six domains** and the same evidence-first task backbone as External (pricing_wtp, operations_time, transportation_logistics, resource_consumption, market_demographics, legal_policy).
- **Same gold**: The evaluation target is always the **target item's** `y_star_evidence` (round(mean(visible evidence))).
- **Conditions**: control, plausible_low, plausible_high, irrelevant_low, irrelevant_high.

### Condition families

- **Control**: Single-stage; full evidence and question only.
- **Plausible (same-case)**: Stage 1 = partial evidence (2-of-5 subset chosen by subset search); Stage 2 = same case with full evidence. Prompt states "same case" and "full evidence now available."
- **Irrelevant (different-case)**: Stage 1 = warmup case in the **same domain** (different case identity); Stage 2 = target case. Prompt states "new case from the same domain" and "previous answer was for a different case."

## Domain consistency with External

- History items are generated from the **same domain config** as External: same `DOMAINS`, scenario templates, evidence labels, question templates.
- Cross-suite comparison (History vs External) differs **only in anchor source** (conversation history vs external sentence), not in domain mix or task structure.

## How to generate the dataset

From the repo root:

```bash
# Pilot (all 6 domains, 5 items per domain × difficulty)
anchorbench generate data=history +size=pilot seed=42

# Smoke (1 domain, quick check)
anchorbench generate data=history +size=smoke seed=42
```

Outputs:

- `itemspecs.jsonl`: One ItemSpec per item (suite=history, `history` dict with subset indices, warmup data).
- `promptviews.jsonl`: Five PromptViews per item (control + plausible_low/high + irrelevant_low/high). Non-control views have `prompt_components.stage1_user_message` and `prompt_components.stage2_user_message`.
- `manifest.json`: Counts and paths.

## How to run evaluation

Two-stage conditions require running Stage 1, then Stage 2 with the model's Stage 1 reply in the conversation:

```bash
anchorbench eval data=history model=llama_8b

# or invoke the runner directly, e.g. to pick a non-default baseline:
python -m anchorbench.runners.history \
  --promptviews datasets/anchorbench_history_core/promptviews.jsonl \
  --itemspecs   datasets/anchorbench_history_core/itemspecs.jsonl \
  --model_id meta-llama/Llama-3.1-8B-Instruct \
  --out_dir results/history_check \
  --backend vllm --max_tokens 512 \
  --baseline_condition control_twostage
```

- **Control**: One call per item (single-stage).
- **Plausible / Irrelevant**: Stage 1 call, then multi-turn Stage 2 (user → assistant → user) using the runner's `generate_chat`.

## Output fields

- **results.jsonl** (one line per item × condition):
  - `item_id`, `suite`, `domain`, `condition`, `anchor_relevance`
  - `y_star_evidence`, `answer_int` (Stage 2 answer for non-control; single answer for control)
  - `stage1_answer`, `stage1_raw_text` (set for non-control)
  - `parsed_ok`, `parse_strategy`, `raw_text` (Stage 2 raw for non-control)
- **summary.json**:
  - **Plausible**: `acr_mean_plausible`, `rr_mean_plausible`
  - **Irrelevant**: `shift_irrelevant_low`, `shift_irrelevant_high`, `shift_high_low_contrast`, `toward_anchor_rate_irrelevant`
  - **Accuracy**: `mae_overall`, `accuracy_within_10`, `parse_rate`, `mae_by_condition`

## Validators

- **Itemspec**: `history` dict present; subset indices in [0,4]; low/high subset means bracket `y_star_evidence`; warmup_low/warmup_high have `evidence_structured` and `y_star_evidence`.
- **PromptView**: Control has no `stage1_user_message`; non-control has `stage1_user_message` and `stage2_user_message`; `anchor_relevance` matches condition.

## Limitations

- **Control vs two-stage**: Control is single-stage; other conditions are two-stage. A possible confound is that differences may partly reflect **history structure** (having a prior turn) rather than anchoring. An optional **neutral_history** condition (two turns, non-numeric Stage 1) is documented in the plan for internal validation only.
- **Stage 1 value**: Direction (low/high) is controlled by subset or warmup design; the exact Stage 1 number is model-dependent.
- **Determinism**: With temperature=0, two-stage runs can still vary across environments.
- **Context length**: Multi-turn prompts use more context; long conversations may hit context limits.
