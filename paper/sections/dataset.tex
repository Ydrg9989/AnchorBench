We present \textsc{AnchorBench}, a benchmark for measuring
anchoring in LLM numeric estimation.
Unlike prior work that tests a single anchor-delivery mechanism
and treats all numeric sensitivity as equally undesirable,
\textsc{AnchorBench} is organized around two orthogonal axes:
the \emph{source} through which anchors reach the model
(mapped to human anchoring paradigms) and the \emph{relevance}
of the anchor (determining whether sensitivity is rational).

\subsection{Anchor-relevance axis}
\label{sec:relevance-axis}

The benchmark's key methodological innovation is separating
anchor \emph{source} from anchor \emph{relevance}.
Not all numeric sensitivity is irrational: a model that adjusts
its estimate toward a validated prior is behaving differently
from one that shifts toward an arbitrary batch number.
We define four relevance levels:

\begin{itemize}
\item \textbf{None} (control):
  No anchor-bearing numeric cue appears beyond the task
  evidence.  The model should rely on evidence alone.

\item \textbf{Irrelevant}:
  A transparently arbitrary number with no evidential relation
  to the target (\eg a case~ID, batch number, or sequential
  request index).
  A well-calibrated model should exhibit near-zero sensitivity.

\item \textbf{Plausible}:
  A weakly credible, plausibly related numeric cue
  (\eg ``a recent industry report suggested\ldots''), but not
  validated enough to override the provided evidence.
  Limited sensitivity may be defensible, but the model should
  remain primarily evidence-driven.

\item \textbf{Informative}:
  A genuinely task-relevant signal (\eg a validated prior-quarter
  measurement).
  Some sensitivity is desirable if the signal is genuinely
  predictive.
\end{itemize}

\noindent The core benchmark conditions are
\texttt{control} + \texttt{irrelevant\_low} +
\texttt{irrelevant\_high} + \texttt{plausible\_low} +
\texttt{plausible\_high} (5~prompt views per item).
The \texttt{informative} level is reserved for optional
validation experiments.
This design enables the benchmark to measure both
\emph{susceptibility} (overall shift toward anchors) and
\emph{discrimination} (whether sensitivity depends on
relevance).

\subsection{Evidence-first task construction}
\label{sec:gold-rule}

Every item presents the model with a numeric estimation task
in which structured evidence is the primary input.
The construction ensures that a deterministic gold answer is
derivable from the evidence alone, independent of any anchor.

\paragraph{Latent signal.}
For each item, a latent parameter $\theta$ is drawn uniformly
from $[30, 70]$ (seed-controlled).
Five numeric ratings are sampled i.i.d.\ from
$\mathcal{N}(\theta, \sigma^{2})$ with $\sigma = 8$, clamped
to $[0,100]$ and rounded to integers.
The evidence is purely informational and correctly centered
on~$\theta$; no anchor enters the evidence block.

\paragraph{Gold answer.}
The evaluation target is
$y^{*}_{\text{evidence}} = \mathrm{round}(\overline{e})$,
the rounded mean of the evidence values actually presented to
the model.
This ensures that a model performing correct evidence
aggregation receives full credit, regardless of sampling
noise between $\theta$ and the evidence mean.
The latent $\theta$ is retained as
$y^{*}_{\theta}$ for understanding the data generation
process but is not the primary evaluation target.

\paragraph{Anchor construction.}
Anchors are placed symmetrically around $\theta$ using
stratified offsets $\delta \in \{15, 25, 40\}$:
$a_{\text{low}} = \max(0,\, \theta - \delta)$, \;
$a_{\text{high}} = \min(100,\, \theta + \delta)$.
Item generation iterates over offset levels to ensure balanced
coverage, enabling analysis of whether anchoring effects scale
with anchor--target distance.
(For the History suite, the anchor is the model's own
Stage~1 answer rather than an experimenter-defined value;
see \S\ref{sec:metrics}.)

\paragraph{Domains.}
Each item asks the model to estimate a domain-specific index on
a $0$--$100$ scale.
Six domains span distinct estimation contexts to avoid
domain-specific confounds: pricing / willingness-to-pay,
operations / time estimation, transportation / logistics
reliability, resource consumption / efficiency, market /
demographics adoption, and legal / policy compliance.
Each domain defines five evidence-label families, multiple
scenario templates, question templates requesting a 0--100
integer, and relevance-specific anchor-preamble templates.

\paragraph{Difficulty axis.}
Items vary in estimation difficulty:
\begin{itemize}
\item \textbf{Easy}: five concordant ratings with
  $\sigma = 8$; the evidence mean is close to $\theta$
  and the answer is straightforward to derive.
\item \textbf{Hard}: three ratings (two marked as unavailable)
  with $\sigma = 15$ and one conflicting value; the
  evidence is sparse and ambiguous.
\end{itemize}
The human anchoring literature predicts that anchoring is
stronger under uncertainty~\citep{chapman1999anchoring};
this axis enables testing that prediction in LLMs.

\subsection{Benchmark suites}
\label{sec:suites}

Each suite instantiates a specific human anchoring paradigm
through a realistic LLM interface.
For each suite we state: (1)~what paradigm it instantiates,
(2)~why the interface is realistic, and (3)~what a rational
model should do under the relevance axis.

\paragraph{External suite (Paradigm~P1: classic external
  anchoring).}
The anchor appears as a sentence in the prompt text,
replicating the classic paradigm from
\citet{tversky1974judgment} in which an experimenter provides
a numeric reference point before eliciting a judgment.
This is the most direct LLM interface for external anchoring:
users, system prompts, or upstream pipelines routinely embed
numeric cues in prompt context.
\emph{Irrelevant condition:}
  ``\textit{Note: This is assessment case \#$a$ in the current
  evaluation batch.}''---a transparently arbitrary identifier.
\emph{Plausible condition:}
  ``\textit{A recent industry report suggested the [metric]
  index might be around~$a$.}''---a weakly credible estimate
  from an unspecified source.
\emph{Rational behavior:}
  A well-calibrated model should show near-zero shift for the
  irrelevant case~ID and at most limited shift for the
  plausible report, remaining primarily evidence-driven in both
  cases.
Control prompts omit the anchor sentence entirely.
A strict pairing invariant is enforced: anchored and control
prompts differ only in the anchor-bearing sentence.

\paragraph{History suite (Paradigm~P2: self-generated
  anchoring).}
The anchor originates from the model's own prior estimate,
instantiating \citet{epley2001putting}'s self-generated
anchoring paradigm, in which insufficient adjustment from a
self-produced starting point biases the final judgment.
In deployed chat systems, a model's own prior output---cached in
the conversation turn---can anchor subsequent estimates.
We implement a genuine two-stage protocol with two condition
families:
\emph{Plausible (same-case):}
  In Stage~1, the model estimates from a partial-evidence
  subset (2~of~5 ratings selected to bias the initial estimate
  low or high).
  In Stage~2, full evidence is revealed in the same
  conversation and the model re-estimates.
  The Stage~1 answer becomes a self-generated anchor;
  insufficient adjustment toward the evidence-supported answer
  constitutes anchoring.
\emph{Irrelevant (different-case):}
  In Stage~1, the model answers a warm-up item from the same
  domain but a different case (with evidence designed to
  produce a low or high estimate).
  In Stage~2, the target item is presented as explicitly new,
  with the warm-up answer retained in conversation history.
  Any influence of the irrelevant warm-up answer on the target
  estimate constitutes anchoring.
\emph{Control:}
  A single-stage prompt with full evidence and no prior
  history, identical to the external-suite control.
\emph{Rational behavior:}
  Under plausible conditions, a rational model should adjust
  nearly completely from its Stage~1 estimate toward the
  full-evidence answer.
  Under irrelevant conditions, it should produce estimates
  indistinguishable from control, since the warm-up answer
  pertains to a different case.

\paragraph{ICL suite (Paradigm~P3: numeric priming).}
Three few-shot demonstrations precede the target question.
This suite instantiates
\citet{mussweiler1999hypothesis}'s selective accessibility
model: irrelevant numbers in the demonstration context may
prime anchor-consistent retrieval of numeric knowledge, even
when the numbers have no evidential relation to the target.
Few-shot prompting is a standard LLM interface, and
demonstration context routinely contains incidental metadata
(example IDs, dataset indices, timestamps) that could function
as numeric primes.
In the current design, demo answers are kept neutral to isolate
the priming effect of metadata numbers from ICL
distribution-matching.
\emph{Irrelevant condition:}
  Demo headers include case IDs and batch numbers near the
  anchor value: ``\textit{Example~1 [Case~\#$a$, Batch~$a$]:
  \ldots}''
\emph{Rational behavior:}
  Metadata identifiers carry no information about the target
  quantity; a well-calibrated model should show no sensitivity
  to these numbers.

\paragraph{RAG suite (Paradigm~P4: ecological anchoring).}
The anchor appears within a retrieved document, reflecting a
realistic deployment scenario in which a retrieval-augmented
system surfaces documents containing task-related (or
task-unrelated) numeric content.
This is not a direct instantiation of a classic psychology
paradigm but rather an ecological extension: in deployed RAG
pipelines, models routinely encounter numeric values in
retrieved passages whose relevance varies from incidental to
highly informative.
Each item has a frozen three-document mini-corpus:
(i)~a \emph{core} document providing genuinely relevant domain
context (no anchor),
(ii)~a \emph{filler} document with neutral methodological
background (no anchor), and
(iii)~an \emph{anchor-slot} document whose content varies
across conditions.
Retrieval is deterministic: documents are presented in fixed
order [core, anchor-slot, filler], ensuring that the only
variation across matched conditions is the anchor-slot
document content.
\emph{Control condition:}
  The anchor-slot document is a neutral administrative note:
  ``\textit{No external benchmark data was located for this
  assessment case.}''
\emph{Irrelevant condition:}
  The anchor-slot document states:
  ``\textit{Administrative note: document batch reference
  \#$a$. This identifier is assigned sequentially and is
  unrelated to assessment content or outcomes.}''
\emph{Plausible condition:}
  The anchor-slot document states:
  ``\textit{A recent survey of comparable organizations
  reported a [metric] index of approximately~$a$.}''
\emph{Rational behavior:}
  Administrative metadata should be ignored entirely;
  a plausible survey result may warrant limited attention
  but should not override direct evidence.

\paragraph{Tool suite (Paradigm~P4: ecological anchoring).}
The anchor is returned within a structured tool output rendered
using the model's native tool-calling chat template (with
\texttt{role:~"tool"} messages), making the framing
structurally distinct from prompt-embedded text.
In deployed agentic systems, LLMs routinely receive structured
JSON data from external tools---APIs, database lookups,
monitoring dashboards---whose outputs contain both informative
fields and incidental metadata (request IDs, batch indices,
sequence numbers).
Two deterministic tools are available:
\texttt{get\_evidence\_summary} (computes summary statistics
over the evidence ratings) and
\texttt{check\_external\_reference} (looks up external
benchmark data for a domain).
The prompt includes a simulated tool-call exchange: the
assistant issues both tool calls, and the tool responses
appear as structured \texttt{role:~"tool"} messages.
The \texttt{get\_evidence\_summary} output is identical across
all conditions; only \texttt{check\_external\_reference}
varies:
\emph{Control condition:}
  \texttt{\{"status": "no\_data", "note": "No external
  reference available\ldots"\}}.
\emph{Irrelevant condition:}
  \texttt{\{"request\_id": $a$, "status": "no\_data",
  "note": "Request ID is a sequential processing
  identifier\ldots"\}}---the anchor appears only as a metadata
  field explicitly labeled as unrelated to content.
\emph{Plausible condition:}
  \texttt{\{"reference\_value": $a$, "source":
  "industry\_survey\_2025", "confidence": "low"\}}---the anchor
  is a nominally informative but low-confidence benchmark value.
\emph{Rational behavior:}
  A request~ID is pure metadata and should be ignored; a
  low-confidence benchmark value from an unverified survey
  may warrant limited attention but should not override
  direct evidence.
An ecological validation subset additionally tests a small
number of items (${\sim}50$) through genuine multi-turn
function-calling interaction, where the model generates tool
calls, receives executed results, and produces a final answer,
validating that the injected results generalize to authentic
agentic behavior.

\paragraph{Scale.}
The external-suite pilot uses 90~items $\times$ 5~conditions
$=$ 450~prompts across 6~domains.
The history-suite pilot uses 60~items $\times$ 5~conditions
$=$ 300~prompts across the same 6~domains, with each
non-control condition requiring a two-stage conversation.
The RAG-suite pilot uses 180~items $\times$ 5~conditions
$=$ 900~prompts across 6~domains, with a frozen
three-document corpus per item.
The tool-suite pilot uses 180~items $\times$ 5~conditions
$=$ 900~prompts across 6~domains, with structured tool outputs
rendered via the model's chat template.
The ICL-suite pilot uses 180~items $\times$ 5~conditions
$=$ 900~prompts across 6~domains, with three few-shot
demonstrations whose metadata headers carry the anchor.
The full benchmark targets 5~suites $\times$ 6~domains
$\times$ 20~items $\times$ 2~difficulty levels $= 1{,}200$
\textsc{ItemSpecs}, each producing 5~\textsc{PromptViews},
for 6{,}000~total prompts.
All generation is seed-controlled (seed $= 42$) and
deterministic.

\subsection{Prompt structure and validation}
\label{sec:prompt-structure}

All prompts end with: ``\textit{Return only a single integer
0--100 on the last line.}''
Each \textsc{PromptView} stores the full prompt text,
structured prompt components, anchor string and character-offset
span (for mechanistic analyses), and a prompt hash for
integrity checks.

Deterministic validators verify:
(i)~$\theta \in [30,70]$,
$y^{*}_{\text{evidence}} = \mathrm{round}(\overline{e})$,
anchors in $[0,100]$, offset $\delta \in \{15, 25, 40\}$;
(ii)~evidence ratings are present, in $[0,100]$, and consistent
with domain labels;
(iii)~control and anchored prompts differ by at most the
anchor-bearing component;
(iv)~RAG document assertions and tool-call schemas are valid;
(v)~all prompts contain the answer-format instruction.
All five pilot datasets (external, history, ICL, RAG, tool)
pass all validators with zero errors.
The history-suite validator additionally checks that
partial-evidence subsets bracket the gold answer and that
warm-up cases are drawn from the same domain as the target.
The RAG-suite validator verifies that the three-document
corpus is present, that anchor-slot documents contain the
correct anchor value, and that retrieved document IDs are
consistent across conditions.
The tool-suite validator checks that anchor values appear in
the correct tool-output JSON field (\texttt{request\_id} for
irrelevant, \texttt{reference\_value} for plausible), that
\texttt{get\_evidence\_summary} output is identical across all
conditions, and that prompt hashes are unique per condition.
The ICL-suite validator checks that all five conditions share
identical target evidence, scenario, question, demo evidence,
and demo answers; only the demo header metadata differs
across matched conditions.
